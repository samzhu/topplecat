# ToppleCat 0.0.2 Release Documentation Design

## Status

Approved for implementation after the 0.0.2 verify exit-signal fix is complete.

## Purpose

Prepare an accurate, bilingual release-documentation set for the completed
0.0.2 core-correctness work and the approved verify exit-signal fix. The
repository has not been tagged, pushed, or published to Maven Central, so the
documentation must describe 0.0.2 as a release candidate / release preparation
and must not claim that a remote artifact is available.

The exit-signal change is a release-documentation prerequisite. Its release
note and normative documentation must not describe the new non-`PASS` exit
behavior until the implementation and regression tests are present in the
current tree.

## Release-note Content

Each language version will contain the same six sections:

- **Status and compatibility:** Version 0.0.2 is prepared but not remotely
  published; Java 25 and the documented Gradle baseline remain required; no
  public evidence or `agent-feedback.json` schema changes are introduced.
- **Expected-value correctness:** A top-level `expected` key counts only when
  `ToppleCase.verify(...)` asserts it. Reading through `expected(...)` no
  longer satisfies enforcement. This prevents a green test from treating
  deserialization as proof.
- **JSON numeric correctness:** Recursive comparison uses exact mathematical
  numeric equality, so `200`, `200.0`, and `200.00` compare equal, including
  in nested objects and arrays, while structural differences continue to fail.
- **Reviewer escrow update:** Authorized reviewers can restore, edit, check,
  review, and run `toppleCatUpdateEscrow`. The task stages and validates the
  revised reviewer source, writes reviewer-local metadata-only audit counts,
  performs a validated staged activation, retains the old custody state until
  activation, and safely recovers on failure. The implementation requests
  atomic moves where the filesystem supports them and otherwise retains the
  same validation and recovery path. Ordinary `toppleCatHide` still rejects
  changed restored source.
- **Public-contract mutation scope:** Default PIT is explicitly limited to
  `sourceSets.test`; reviewer rows and reviewer-only JUnit tests remain a
  separate retest safeguard and cannot inflate the public mutation score.
- **Trustworthy terminal signal:** After all evidence, reports, and safe agent
  feedback have been written, `toppleCatReport` and therefore
  `toppleCatVerify` fail the Gradle build whenever the aggregate verdict is
  `FAIL` or `INCOMPLETE`. A green final gate therefore means `PASS`; explicit
  `DISABLED` safeguards keep their existing aggregate semantics. This section
  is included only after the approved exit-signal implementation and regression
  tests are committed.

The notes will also state the verification evidence from the final integrated
tree: targeted functional tests, the full Gradle check, and
`scripts/verify-release.sh` completed successfully. They will not expose
reviewer values, identifiers, paths, source names, or raw failures.

## README and Guide Changes

The README installation section will retain the intended `0.0.2` coordinates
as the upcoming release coordinates, but will label them as pending remote
publication. It will point source-checkout contributors to
`publishToMavenLocal` and clearly state that this is local validation rather
than publication. The documentation index will link to the release note in its
matching language.

The getting-started guide will make the same publication-status distinction.
The sample index and both tutorials will describe `publishToMavenLocal` only as
source-checkout validation and will not direct a reader to an unavailable
remote 0.0.2 artifact.

The authoring guide will link readers to the numeric and expected-consumption
release details. The verification guide will link readers to the escrow-update
and PIT-boundary release details, and it plus troubleshooting will state the
new terminal exit behavior after that fix is implemented. These guides remain
normative for workflow; the release note is explanatory and version-specific.

## Boundaries and Verification

- Do not modify production code, test code, public evidence schemas, or safe
  feedback schemas.
- Do not tag, push, create a pull request, or publish remotely.
- Do not add reviewer-only data to public documentation.
- Do not overwrite or discard pre-existing README or guide edits. Inspect the
  live diff immediately before editing, integrate at the paragraph level, and
  stage only the release-documentation files owned by this work.
- Do not claim the exit-signal behavior until its production and regression
  changes exist in the current commit history.
- Validate Markdown with `python3 scripts/verify-docs.py` and inspect the
  final diff for consistency between English and Traditional Chinese content.
- After all 0.0.2 code and documentation are integrated, rerun
  `./gradlew check` and
  `GRADLE_CMD=./gradlew scripts/verify-release.sh` before recording successful
  verification in the release notes.

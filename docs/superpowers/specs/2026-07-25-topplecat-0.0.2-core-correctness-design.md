# ToppleCat 0.0.2 Core Correctness Design

## Status

Approved direction, pending review of this written design.

## Product Goal

ToppleCat exists to help a human reject an AI agent's false done claim:
shortcut implementations, hollow tests, incorrect behavior, and unverifiable
results must not receive a trustworthy `PASS`.

This release repairs behavior that can produce a false verdict or prevent the
reviewer suite from evolving with the public contract. It does not broaden
ToppleCat into a general test-management, requirements-management, reporting,
or remote-attestation product.

## Release Scope

ToppleCat `0.0.2` will make four focused changes:

1. Require every declared expected value to reach `ASSERTED`.
2. Compare JSON numeric values by exact mathematical value rather than JSON
   numeric node representation or decimal scale.
3. Add an explicit reviewer-only workflow for updating an existing escrowed
   reviewer suite.
4. Define and protect the mutation gate as a measurement of the public
   executable contract only.

The Java acceptance tests and typed JSON/YAML rows remain authoritative.
Generated evidence and reports remain projections. No second authoring language
or command-line interface is introduced.

## 1. Expected-Consumption Correctness

### Problem

`ToppleCase.expected(...)` deliberately records `READ`, because reading expected
data is not an assertion. The current enforcement checks only for `UNTOUCHED`.
An agent can therefore read an expected value, never compare it with production
output, and still pass expected-consumption enforcement.

That violates the product promise that every declared result was actually
verified.

### Required Semantics

When expected-consumption enforcement is enabled:

| State | Meaning | Result |
| --- | --- | --- |
| `ASSERTED` | `c.verify(...)` compared expected with actual | Pass |
| `READ` | Expected data was read but not verifiably asserted | Fail |
| `UNTOUCHED` | Expected data was never used | Fail |
| Missing/unknown sidecar state | The run cannot prove consumption | `INCOMPLETE` |

When enforcement is explicitly disabled, all states are still recorded, but
neither `READ` nor `UNTOUCHED` causes a test failure. Evidence must continue to
record the gate as `DISABLED`, not `PASS`.

JUnit enforcement and report/evidence aggregation must implement the same
predicate: only `ASSERTED` satisfies an expected obligation. The implementation
must avoid one path treating `READ` differently from the other.

### Diagnostics

The failure message must identify the affected `expected.<key>` and instruct the
author to call `c.verify("<key>", actual)`. It may distinguish `READ` from
`UNTOUCHED`, but it must not add reviewer values, expected values, source paths,
test names, or stack traces to `agent-feedback.json`.

If another test failure already exists, ToppleCat must preserve that original
failure while still recording the expected-consumption state for reviewer
evidence.

### Acceptance Criteria

- A test that calls only `c.expected("receipt", ...)` fails when enforcement is
  enabled.
- The same read-only case makes the final `EXPECTED_CONSUMPTION` gate fail.
- A completely untouched expected key also fails.
- A key verified with `c.verify(...)` passes.
- With enforcement disabled, `READ` and `UNTOUCHED` remain visible in reviewer
  evidence but do not independently fail the test.
- Public `agent-feedback.json` remains gate-level and contains no reviewer
  details.

## 2. Numeric Contract Equality

### Problem

Typed Java output can represent a valid amount as `BigDecimal("200.00")`, while
JSON or YAML case data may be parsed as `200`, `200.0`, or another numeric node.
Comparing the resulting JSON nodes by concrete node type or decimal scale can
reject mathematically equal values and encourage an incorrect production model
such as `double` for money.

### Required Semantics

`ToppleCase.verify(...)` must perform recursive contract equality:

- When both nodes are numeric, compare their arbitrary-precision decimal values
  with exact mathematical equality. There is no epsilon or approximate
  tolerance.
- `200`, `200.0`, and `200.00` are equal.
- Numerically different values remain unequal.
- Objects must contain the same field names, and each corresponding value must
  compare recursively.
- Arrays must have the same length and order, and each element must compare
  recursively.
- Strings, booleans, binary values, and null retain exact JSON equality.
- A numeric node and a textual node are not equal.

Decimal scale is not implicitly part of a JSON numeric contract. If a business
contract must assert formatting or scale, it must express that requirement as a
string or a separate explicit output field.

The mismatch diagnostic remains the existing expected-versus-actual assertion
message. Hidden values continue to appear only in reviewer-controlled failures
and reports, never in safe agent feedback.

### Acceptance Criteria

- Equal integral, floating, and decimal node representations pass.
- Equal numeric values pass when nested inside DTO objects, maps, and arrays.
- A real numeric difference fails.
- Object field omissions/additions and array order changes still fail.
- Numeric text such as `"200.00"` does not equal numeric `200.00`.
- Existing typed input conversion and expected-consumption tracking are
  unchanged.

## 3. Reviewer Escrow Evolution

### Problem

The first `toppleCatHide` establishes an exact escrow manifest. After an
authorized reviewer restores the suite and adds, changes, or removes reviewer
files for a new Spec, the existing hide operation refuses the mismatch. This
protects against accidental replacement, but it also prevents normal project
evolution.

Silently teaching `toppleCatHide` to accept any mismatch would remove that
protection. Updating custody must therefore remain a separate, explicit reviewer
action.

### Workflow

Add one Gradle task within the existing ToppleCat plugin task surface:

```text
toppleCatRestore
    -> edit src/hiddenTest
    -> toppleCatCheck
    -> toppleCatReview
    -> reviewer inspects and accepts the current review
    -> toppleCatUpdateEscrow
```

`toppleCatUpdateEscrow` is a reviewer-custody command. It is not part of the
implementation loop. The task exists wherever the Gradle plugin is applied, but
a public implementation export contains neither reviewer source nor escrow, so
the task has no custody state to update and must fail safely.

The task must depend on current `toppleCatCheck` and `toppleCatReview` output so
an invalid or unreviewable contract cannot be escrowed through the update path.
Running the explicit update command represents the local reviewer's
authorization; ToppleCat does not claim to authenticate a human identity.
The generated review remains reviewer-only, and the later implementation
handoff must still exclude `.git`, `.topplecat/`, `build/`, and
`src/hiddenTest`.

### Preconditions

The update must fail without changing custody state unless all conditions hold:

- An existing, readable escrow manifest is present.
- The manifest state is `RESTORED`.
- Existing escrow content still validates against the pre-update manifest.
- The reviewer source root can be inventoried and every file can be hashed.
- Static contract checking and reviewer review generation completed for the
  current source.
- The project-scoped custody lock is held exclusively.

Calling ordinary `toppleCatHide` with changed restored source must continue to
fail and direct the reviewer to the explicit update workflow.

### Update Guarantees

The update operation must:

1. Inventory the new reviewer source and calculate a new manifest.
2. Prepare a revision staging area away from the active snapshot.
3. Validate the planned snapshot and manifest before changing the active state.
4. Record the previous and new manifest digests plus added, changed, and removed
   file counts in reviewer-local audit metadata.
5. Atomically move the complete restored reviewer source into the staged
   revision, so no per-file deletion can leave a partly visible source tree.
6. Validate the staged revision after the move.
7. Atomically switch the active escrow reference to the validated revision.
8. Finish in `HIDDEN` state.

No audit record may copy source contents, input values, expected values, or raw
failures. Reviewer file paths may remain inside `.topplecat/`, which is already
reviewer-only plaintext custody, but they must not enter public evidence,
reports, or agent feedback.

If an error occurs before activation, the previous active escrow remains valid.
If the source move or active-reference switch fails, the operation must either
restore `src/hiddenTest` completely or retain the staged revision with an
explicit recovery instruction. It must never report `HIDDEN` while a partial
reviewer source tree remains visible.

The on-disk format may evolve to a new escrow schema or revisioned snapshot
layout. Existing version-1 escrow must remain readable. Its first authorized
update may migrate it, but ordinary restore, exact re-hide, and verification
must continue to work before and after migration.

### Acceptance Criteria

- Initial hide, exact restore, exact re-hide, and verification behavior remain
  unchanged.
- After restore, adding a reviewer file can be explicitly updated and hidden.
- Modifying and removing reviewer files follow the same explicit update path.
- Ordinary hide still rejects a changed restored suite.
- Update from `HIDDEN` state is rejected.
- Missing, corrupt, or mismatched prior escrow is rejected without replacing
  the valid material that remains.
- A failed staged update leaves the prior active escrow restorable.
- Verification uses the updated reviewer suite and re-hides it afterward.
- Public reports, evidence, and agent feedback reveal no update metadata or
  reviewer details.

## 4. Public-Suite Mutation Semantics

### Product Meaning

The mutation gate answers:

> Can the public executable contract detect broken production behavior?

Hidden retests answer a different question:

> Did the implementation generalize beyond the visible examples, or did the
> agent take a shortcut?

Reviewer-only cases and reviewer-only JUnit tests must not help the default PIT
producer kill mutants. Otherwise a hollow public contract could receive a
mutation `PASS` because secret tests supplied the missing assertions.

### Required Behavior

- The default mutation producer uses public test classes and public case rows
  only.
- Hidden rows and reviewer-only JUnit tests remain excluded from the default PIT
  run even though they execute elsewhere in `toppleCatVerify`.
- Mutation attribution remains canonical-method based.
- A mutant legitimately covered by two public canonical methods may affect both
  ACs; this is not class-level duplication.
- No per-case mutation score is added in this release.
- Documentation and task descriptions must call the result public-contract
  mutation strength rather than implying combined public/reviewer mutation
  strength.

A regression fixture must prove that a boundary covered only by reviewer data
does not kill a public-suite mutant. Making that boundary part of the public
contract is the correct repair when the public contract is supposed to detect
it.

Custom mutation producers remain an advanced reviewer responsibility. This
release does not add a new producer-scope schema or attempt to infer the test
scope of arbitrary third-party tasks.

## Compatibility

The following public contracts remain unchanged:

- Plugin ID and published module coordinates.
- Java annotations and Stage authoring rules.
- Four-field JSON/YAML case schema.
- Evidence and `agent-feedback.json` schemas.
- Gate names and aggregate verdict meanings.
- Default 100% per-AC mutation threshold.

The explicit escrow update task is an addition to the existing Gradle plugin
workflow. Any escrow schema migration is internal local-custody compatibility
and must read existing version-1 state.

The intended release is `0.0.2`; the existing `v0.0.1` tag and artifacts must
not be rewritten.

## Non-Goals

This release will not:

- Run hidden tests in the default mutation producer.
- Add per-case mutation execution or scores.
- Add failed AC IDs, reviewer categories, source lines, mutator names, stack
  traces, or case details to safe agent feedback.
- Add production-source or compiled-class digests to evidence.
- Parse Spec Kit functional requirements or generate Spec Kit task files.
- Add a second authoring language, standalone CLI, service, database, or remote
  custody mechanism.
- Claim cryptographic secrecy, reviewer identity authentication, or portable
  remote attestation.

## Verification Strategy

Development must begin with narrow regression tests for each confirmed failure:

1. A read-only expected key that currently passes.
2. Equal JSON numeric values with different node representations.
3. A restored reviewer suite that cannot currently be updated.
4. A mutant covered only by reviewer data.

After the narrow tests pass, run:

```bash
./gradlew check
GRADLE_CMD=./gradlew scripts/verify-release.sh
```

The release is complete only when:

- All narrow regression tests pass.
- The complete repository checks pass.
- Both checked-in sample FAIL-to-PASS demonstrations still behave as designed.
- The mutation integration fixture still fails for its deliberate survivor.
- Documentation and skill validation pass.
- Generated `build/`, `.topplecat/`, credentials, and temporary reviewer data
  are absent from the commit.

## Downstream Implementation Boundary

The implementing agent may change production code, tests, and public
documentation required by this design. It must not:

- Open or reuse real reviewer values from an unrelated project.
- Copy the evaluation fixture's hidden values into this repository.
- Change `agent-feedback.json` or evidence schemas.
- Include reviewer tests in default PIT.
- Add Spec Kit-specific behavior.
- Broaden the release beyond the four scoped changes.

When implementation is reported done, an independent review must compare the
result against every acceptance criterion in this document and rerun both
repository verification commands before accepting the claim.

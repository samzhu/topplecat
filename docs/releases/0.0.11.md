# ToppleCat 0.0.11

0.0.11 gives reviewers two clear human reports: a complete Spec Review before
handoff and a failure-first Verification Report after formal Verify. The
generated HTML no longer competes with the Java/JUnit contract or hides the
useful finding behind report mechanics.

## Upgrade: stop consuming the retired public HTML

`build/topplecat/reports/public/` is no longer produced. ToppleCat now removes
an old bundle at that fixed generated path during formal report publication.
Implementation agents continue to receive the original public source contract
and safe `agent-feedback.json`; there is no replacement public HTML.

Code that directly used the `SpecView` projection or its report JSON/writer
methods must remove that integration. Reviewer tooling that reads report
`data.json` must adopt `topplecat.review-view.v7` and
`topplecat.verification-view.v9`. There is no compatibility reader or dual
writer for the old report projections.

The public Java/JUnit acceptance-authoring API, Gradle task names, `--spec`
selection, six Gate names, aggregate verdict, and machine evidence schemas are
otherwise unchanged.

## Read the complete selected Spec before handoff

`toppleCatReview --spec ...` now produces **Spec Review**. It renders each
complete selected Markdown document before the executable material bound to
its ACs, including readable Given/When/Then/And syntax, public and reviewer
Typed Case Rows, Properties, Contract Quality Advisories, and the complete
public Acceptance Method source.

The offline report supports structured Markdown, tables, fenced code, local
images, syntax highlighting, and safe Mermaid flowcharts. Unsafe raw HTML and
URLs are escaped. A diagram or local asset that cannot be rendered leaves a
visible fallback instead of silently dropping specification content.

Spec Review is reviewer-only because it contains reviewer rows, source paths,
and quality advisories. It clearly says that the specification is prepared but
has not been executed.

## Find the actual verification problem first

Formal Verify now produces **Verification Report**. Its first screen states
whether the delivery passed, failed, or is incomplete, followed by a Problems
Summary that links to the relevant Gate, AC, case, Property, mutation finding,
or integrity detail.

Contract Integrity, Public Acceptance and Expected Consumption, Hidden Tests,
Property-Based Testing, and Mutation Testing remain separate report areas with
no blended score. A failing case opens on the first real failure rather than a
passing public example.

When `ToppleCase.verify(...)` finds different JSON, the reviewer report shows
structured paths for missing, unexpected, and changed fields, including nested
objects and arrays. The comparison stays bound to the active compiler-described
Step and remains reviewer-only; assertion and Gate semantics do not change.

## Use one managed mutation question across deliveries

Since the previous published GitHub Release, formal Verify now owns PIT 1.25.5
and the fixed `topplecat-managed-v1` operator profile. Remove
`mutationTesting.producerTask` and `mutationTesting.reportFile` when upgrading
from 0.0.8 or earlier. Projects may still run a separate PIT workflow, but it
cannot supply ToppleCat Mutation Gate evidence.

Mutation Attribution matches the exact public Acceptance Method class, method,
overload, and parameter types. Verification Report preserves PIT's raw
`status`, `detected`, mutator, description, and covering/killing/succeeding
selector relationships. It also shows per-AC detection rates and attribution
gaps without inventing a PIT status or blending mutation evidence with Hidden
Tests, Properties, or Mechanical Seal.

A human-lowered threshold may let the Mutation Gate pass while raw surviving
mutants remain visible. Contract Quality Advisory remains a non-blocking human
prompt and never changes a Gate.

## Upgrade actions

1. Update the Gradle plugin and `topplecat-junit` dependency to `0.0.11`.
2. Remove `producerTask` and `reportFile` from `mutationTesting` configuration
   if the project still uses them.
3. Stop publishing or parsing `reports/public` and remove integrations with
   the retired `SpecView` projection.
4. Update reviewer report readers to `topplecat.review-view.v7` and
   `topplecat.verification-view.v9`.
5. Restore reviewer custody, Check, Review, and Reseal before Verify because
   the Mechanical Seal is current-version-only.

## Requirements

Java 25 and the existing compatible Gradle and JUnit requirements are
unchanged. PIT 1.25.5 remains managed internally by formal Verify. Reports are
offline and do not load Mermaid, syntax-highlighting, font, analytics, or UI
code from a CDN.

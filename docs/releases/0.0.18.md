# ToppleCat 0.0.18

ToppleCat 0.0.18 lets Java teams make an implementation agent's done claim
earn a current-run `PASS`: reviewers first read the selected executable
contract, then see exactly which selected Acceptance Condition did—or did not—
detect temporary production changes. It collects the work since the last
published GitHub Release, 0.0.10, so teams can upgrade once rather than
reconstructing intermediate tags.

## Read the selected contract before handoff, then one AC at a time

`toppleCatReview` writes the reviewer-only **Spec Review** before handoff, and
`toppleCatVerify` writes the reviewer-only **Verification Report** after the
formal run. The retired `build/topplecat/reports/public/` bundle is not
produced; implementation agents continue to receive the public Java/JUnit
contract and safe `agent-feedback.json`. Reviewer tooling that reads report
`data.json` must use `topplecat.review-view.v7` and
`topplecat.verification-view.v9`.

Verification Report now puts Contract Integrity in its main summary exactly
once. A matching Mechanical Seal says that downstream AC work ran; a mismatch
or missing integrity proof says that it did not, without presenting unexecuted
ACs as functional failures. Both reviewer reports support `--language zh-TW`;
the choice translates ToppleCat-owned presentation only.

## Make every selected AC detect its own attributed mutations

Mutation Testing now follows the selected delivery scope. For every selected
AC, its unchanged public Acceptance Method must detect every mutation exactly
attributed to it. A mutation that another AC kills can still be undetected for
the AC whose method covered and passed it. The report shows each AC's assessed,
detected, and undetected counts, followed by reviewer-only cards that explain
the undetected production change, available source location, and evidence
limitation.

There is no percentage score or project-wide mutation score. This makes the
failure meaningful: the owning Acceptance Method passed while a behavior it
executed had been changed. Raw PIT results, selectors, source coordinates, and
technical details remain reviewer-only and do not enter safe agent feedback.

To protect exact selected-AC scope, formal Verify stops before PIT when a
selected Acceptance Method shares a test class with an unselected public
Acceptance Method. PIT cannot select the compiler JVM descriptor needed to
separate those methods safely.

## Keep generated Property inputs reviewable

Property-Based Testing now retains every discarded generator input as JSON
evidence and paginates it in Verification Report. Public Acceptance Methods
and Properties use business-readable JUnit `@DisplayName` values, and public
Stage Steps use `@As` sentences, so the human-facing contract explains the
business situation being checked rather than an implementation detail.

## Start from a clearer public project page

The refreshed public project page now leads with the same current-run `PASS`
promise as the reports, explains why independent safeguards cannot substitute
for one another, and keeps the Reviewer’s delivery decision explicit. English
and Traditional-Chinese pages present the same boundary, while the public page
also supplies share and search metadata for the visible site content.

## Upgrade from 0.0.10

1. Update the Gradle plugin and `topplecat-junit` dependency to `0.0.18`.
2. Stop publishing or parsing `reports/public`; remove `SpecView` integrations
   and update reviewer report readers to `topplecat.review-view.v7` and
   `topplecat.verification-view.v9`.
3. Remove `mutationTesting { threshold.set(...) }`. Every attributed mutation
   must now be detected by its own public Acceptance Method; no percentage
   setting replaces that rule.
4. When using `--spec`, either select every public Acceptance Method in a test
   class or move the selected methods into a dedicated class before formal
   Verify.
5. Give public Acceptance Methods and Properties meaningful JUnit
   `@DisplayName` values, and give public Stage Steps `@As` sentences. Restore
   reviewer custody, then run Check, Review, and Reseal before formal Verify.

## Requirements and compatibility

Java 25 and the existing compatible Gradle and JUnit requirements are
unchanged. Formal Verify continues to manage PIT 1.25.5 internally, and the
reviewer bundles remain offline. The report schemas named above remain the
current supported reader contracts; ToppleCat does not provide a compatibility
reader or dual writer for earlier projections.

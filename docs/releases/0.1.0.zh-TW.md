# ToppleCat 0.1.0

ToppleCat 0.1.0 把 handoff 前後的審閱工作接了起來。交給 agent 實作前，
Reviewer 先讀過 selected Spec 和真正會執行的契約；agent 說 done 之後，再用
本次執行、能追到各 AC 的證據檢查交付。最後要不要接受，仍由人決定。

## 從 0.0.10 升級

上一個正式發布的 GitHub Release 是 0.0.10。0.0.11 到 0.0.28 雖然都有 tag，
但沒有發布成 GitHub Release，所以這次升級包含這段期間累積的報告、驗證與操作變更。

1. 將 Gradle plugin 和 `topplecat-junit` dependency 更新為 `0.1.0`。
2. 停止發布或讀取 `build/topplecat/reports/public/`。這個公開報告已經移除，
   實際交付不會再產生替代的 public HTML。
3. 移除對舊 `SpecView` projection 的整合。如果 reviewer tooling 會讀報告的
   `data.json`，請改用 `topplecat.review-view.v7` 和
   `topplecat.verification-view.v10`。舊格式沒有相容 reader，也不會繼續輸出。
4. 移除 `mutationTesting { threshold.set(...) }`。現在每個公開 Acceptance
   Method 都必須抓到精確歸因給自己的 mutation。
5. CI 請使用不帶 `--spec` 或 `--ac` 的 `toppleCatVerify`。Scoped Verify 適合
   Reviewer 快速檢查剛完成的功能，不是完整專案的替代品。
6. `toppleCatSeal` 和 `toppleCatReseal` 不再接受 `--spec`、`--ac` 或
   `--language`。Seal 一律涵蓋完整契約與驗證政策。
7. Reviewer custody 和 Mechanical Seal 只適用目前版本。升級既有 reviewer
   suite 時，請先 Restore，再依序 Check、Review、Reseal，最後才執行正式 Verify。

公開 Java/JUnit Acceptance Method 的主要寫法沒有改，不需要搬動既有測試原始碼。

## 先看完契約，再交給 agent

`toppleCatReview --spec ...` 會產生 reviewer-only 的 **Spec Review**。報告先放
完整的 selected Markdown Spec，再列出各 Acceptance Condition 實際綁定的內容：
Scenario、公開與 reviewer-owned Typed Case Rows、Properties，以及公開
Acceptance Method 原始碼。

這份報告是 handoff 前的閱讀材料，不會執行測試，也不會替人判斷上游 Spec 是否完整。

Agent 完成實作後，`toppleCatVerify` 會產生 reviewer-only 的
**Verification Report**。報告先列出本次 Aggregate Verdict 和需要注意的 AC，
再讓 Reviewer 分別查看 Public Acceptance、Hidden Tests、Expected Result Check、
Property-Based Testing 與 Mutation Testing。

兩份報告都能離線開啟，內容完整包在 bundle 裡，也符合 CSP 限制。Implementation
Agent 仍只會收到公開 Java/JUnit 契約和安全的 `agent-feedback.json`，不會拿到
reviewer-owned rows、私密診斷或 HTML 報告。

## 剛完成的功能可以先驗，但完整封印不切小

不指定範圍的 `toppleCatVerify` 仍會驗證完整契約，也是 CI 應該使用的命令。Reviewer
如果只想先看剛做完的功能，可以重複指定 Spec 路徑或 AC ID，但不能混用：

```bash
./gradlew toppleCatVerify --spec specs/checkout/spec.md
./gradlew toppleCatVerify --ac AC-CHECKOUT-THRESHOLD --ac AC-CHECKOUT-VIP
```

Scoped run 只針對這些 AC 執行 Public Acceptance、Hidden Tests、Property-Based
Testing 與 Mutation Testing。Verification Report 會列出這次選了哪些 AC，也會在
範圍 `PASS` 旁直接註明：這不是完整契約的結果。

Contract Integrity、`toppleCatSeal` 和 `toppleCatReseal` 始終使用完整可執行契約與政策。
如果選定的 Acceptance Method 和未選的公開方法放在同一個 test class，請選取該
class 的全部 AC，或先把方法拆到不同 class，再執行正式 Verify。

## Mutation credit 不再互相借

正式 Mutation Testing 固定使用 ToppleCat 管理的
`topplecat-managed-v1` PIT 1.25.5 profile。專案自己的 PIT task、自訂 producer、
test targeting 和 report 不會混進 ToppleCat evidence。

Mutation Attribution 會完整比對 Acceptance Method 的 class、method、overload
與參數型別。每個 AC 都要靠自己的公開 Acceptance Method，抓到所有由它覆蓋且精確
歸因給它的 mutation。別的 AC 就算殺掉同一個 mutation，也不能代替目前這個 AC
取得 detection credit。百分比 threshold 和 project-wide mutation score 已經移除。

Mutation Testing 也需要一個通過的 Public Acceptance baseline。如果原始程式連公開
案例都沒通過，結果會是 `INCOMPLETE`。這時無法判斷未修改的 Acceptance Method 是否
能抓到另一個暫時加入的 production change。

遇到 AC 沒抓到的 attributed mutation，Verification Report 會列出 assessed、detected
和 undetected 數量，再用 reviewer-only 卡片說明改了什麼、能確認時的來源位置，以及
該 AC 的公開驗收仍然通過。PIT outcome 和 selector 關係留在技術證據裡，不會洩漏到
agent feedback。

## 報告先講發生什麼，再放技術細節

每個 Acceptance Condition 一開始會顯示 ID、標題、狀態、白話結果和五項 safeguard
outcome。發現問題或證據不足的 safeguard 會顯示原因，不必先展開 Gate 或 producer
細節才能知道出了什麼事。

失敗案例會先列出 authored input，再顯示 expected 和 actual 的欄位差異。完整
expected data、Scenario Steps、傳入 Step 的值、raw failure、Gate verdict 和
producer details 都還在，但收進各自的展開區塊。

Reviewer 可以只展開一個 AC，也可以分批展開全部 AC，之後再回到精簡結果。從問題
摘要點進去時，報告會先打開必要內容，避免連到一個仍被收起來的位置。Mutation
Testing 的陌生術語也有繁中說明，原始 PIT 名稱則照原樣保留。

Property completion count 現在只採計完整且屬於本次執行的 lifecycle，並核對 sealed
AC、完整 Java method identity 和 source digest。Counterexample 與 incomplete
terminal outcome 都會如實保留；generator 捨棄的每個輸入也會留下 reviewer evidence。

## 報告可選英文或繁中

Spec Review 和 Verification Report 接受 invocation-only 的 `--language en` 或
`--language zh-TW`，預設是英文。

這個選項只翻譯 ToppleCat 自己的標題、控制項、無障礙文字和說明。Selected Markdown、
`@DisplayName`、`@As`、Typed Case Rows、AC ID、Gate 名稱、verdict、PIT outcome、
producer text 和 raw failure 都維持原文。

切換語言不會改變 Delivery Scope、Executable Contract、Mechanical Seal、
Current-run Evidence、Gate 結果、report JSON 或 `agent-feedback.json`。

## 公開示範和實際交付分開

公開專案頁現在有五個合成的購物車案例，分別說明 Public Acceptance、Hidden Tests、
Property-Based Testing、Mutation Testing 和 Contract Integrity。

Expected Consumption 是 Public Acceptance 裡的預期輸出檢查，不是第六個 Independent
Safeguard。網站上的案例只用來說明產品，不是某次實際交付的 evidence、agent feedback
或 approval。

ToppleCat 只會在本次執行的必要 Gate 全部通過時記錄 `PASS`。這代表 sealed contract
在這次執行通過了既定檢查，不代表 Spec 沒漏規則，也不替 Reviewer 決定是否接受交付。

## 環境需求

仍需要 Java 25 與相容的 Gradle 版本。正式 Verify 會管理 PIT 1.25.5。Reviewer
report bundle 可以離線開啟，不會連外載入 UI、字型、分析程式、syntax highlighting
或 Mermaid runtime。

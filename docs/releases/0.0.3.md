# ToppleCat 0.0.3

ToppleCat 0.0.3 closes a loophole in delegated verification: an agent could
change the public tests, case data, or verification settings after review, then
make its implementation pass the weakened contract.

## Contract changes cannot reuse an old approval

ToppleCat now records the public executable contract and verification policy
that the reviewer approved. If either changes afterward, `toppleCatVerify`
returns `CONTRACT_INTEGRITY: FAIL` before running the remaining gates.

This catches changes such as:

- replacing a difficult expected result with an easier one;
- removing or renaming an acceptance condition; or
- lowering the mutation policy so an incomplete implementation can pass.

The reviewer can approve a legitimate change through Restore, Check, Review,
and `toppleCatUpdateEscrow`. Ordinary Hide and Verify cannot silently replace
the approval.

## Reviewer state no longer lives in the project tree

Reviewer source and approval data now live at
`~/.topplecat/projects/<project-key>/escrow/`, outside the repository. Copying
or cloning a project does not carry that state into another checkout, and
ToppleCat will not create a new approval from public files alone.

## Upgrading

If an earlier version left escrow under the project-local
`.topplecat/escrow/`, run:

```bash
./gradlew toppleCatMigrateEscrow
```

ToppleCat checks the stored reviewer files before moving them. A damaged legacy
escrow remains in place, and concurrent migrations do not remove active
reviewer state.

Version 1 escrow still needs an authorized reviewer to Restore, Check, Review,
and run `toppleCatUpdateEscrow` before it can produce a PASS. See the
[verification guide](../guide/verification-and-evidence.md) for that workflow.

If your CI parses ToppleCat's JSON reports, it will now see an additional
`CONTRACT_INTEGRITY` check. Most users do not need to change anything.

Release verification output is also quieter: it reports a known-bad
implementation as a successful attack check while preserving full diagnostics
for unexpected failures.

## What this release does not protect against

Reviewer-local escrow is local storage, not a sandbox. Run Verify in a trusted
reviewer or CI environment and give the implementation agent only a public
checkout plus safe feedback.

# ToppleCat 0.0.24

ToppleCat 0.0.24 makes it easier to show a team what the verification gate can
catch, while keeping synthetic demonstrations separate from an actual delivery.

## Show what ToppleCat catches without exposing a real delivery

The public project page now has six simulated checkout cases. They explain, in
plain language, how ToppleCat can catch a missed requirement, a memorized
example, an unchecked expected result, an edge case, a weak test, or a changed
acceptance contract. Each case opens its matching synthetic Verification Report
excerpt when a visitor wants the evidence behind the result.

These examples are for people evaluating the product. They are not a public
Verification Report, an Implementation Agent handoff, or evidence from a real
delivery. The product docs now state that boundary explicitly.

## Add verification to the workflow you already use

The Get started page now shows the whole setup: install the Gradle plugin, add
the project-local `topplecat-acceptance` skill for the coding agent, then run
the formal ToppleCat sequence once the feature is implemented. Teams can keep
using Spec Kit, Superpowers, Matt Pocock skills, or their own project workflow;
those tools still choose and shape the work.

ToppleCat 0.0.24 also lets reviewers scan a long Verification Report from its
results, then open exactly the AC detail they need without losing their place.

## Read the important result before opening a long report

Every Acceptance Condition now starts at its key-result layer: ID, title,
status, plain-language result, and five safeguard outcomes remain visible. Use
**Expand this AC** to read every case in one AC, or **Expand all ACs** to open
the report in cancellable browser batches. **This AC: key result only** and
**All ACs: key results only** return the reader to the concise view.

For example, a reviewer can first identify the failed coupon AC, open its cases
and expected-versus-actual difference, then return the full report to key
results. Technical evidence remains a separate collapsed choice, so opening
reader detail does not expose unrelated Gate or producer diagnostics.

Needs Attention links, safeguard links, and URL fragments open the required
reader path before navigating. The report measures its sticky reading toolbar
and active AC row at runtime, so a linked expected value, Scenario execution,
or raw failure lands below the controls on desktop and narrow screens.

## Put the challenged safeguard in focus

The same fixed five-safeguard key-result layer now gives a safeguard that found
a problem or could not be fully assessed visual focus and repeats its recorded
reader-safe reason. Gate meanings, evidence values, and progressive disclosure
behavior do not change.

## See what failed before reading how it ran

Every Acceptance Condition now starts with a five-safeguard summary using
reader outcomes such as **Passed**, **Problem found**, **Comparison completed**,
and **Unable to assess**. Canonical Gate verdicts and producer terms remain in
collapsed technical evidence rather than disappearing or being renamed.

A failed case presents its authored input followed by a field-level table of
expected and actual values. Complete expected data, Scenario execution Steps,
values passed to Steps, and raw failures remain available one level deeper.
The report also states that a business rule absent from the comparison cannot
be treated as checked merely because it appears in an AC title.

## Distinguish a completed comparison from a passing result

Expected Result Check now says **Comparison completed** when every authored
expected value was compared with the program result. That means the comparison
ran; it does not mean the values matched. Public Acceptance and the structured
difference table provide that result.

When Public Acceptance already finds a problem in the original program,
Mutation Testing says **Unable to assess** and explains that the run lacks a
passing baseline. Raw PIT diagnostics may still be inspected, but they are not
presented as an AC Mutation Testing verdict.

## Understand Mutation Testing terms in place

Verification Report now places a localized `ⓘ` control beside Mutation Testing
and its initial mutation-card terms. Hover or keyboard focus shows a short
explanation; clicking or tapping pins it, and Escape or outside interaction
dismisses it. The result remains visible without help, and the control changes
no report JSON, evidence, Gate, or safe agent feedback.

## Upgrade from 0.0.10

The last published GitHub Release was 0.0.10; tags 0.0.11 through 0.0.20 were
not published as GitHub Releases. Teams upgrading directly from 0.0.10 should:

1. Update the Gradle plugin and `topplecat-junit` dependency to `0.0.24`.
2. Stop publishing or parsing the retired `build/topplecat/reports/public/`
   bundle and remove integrations with the retired `SpecView` projection.
3. Update reviewer report readers to `topplecat.review-view.v7` and
   `topplecat.verification-view.v10`. There is no compatibility reader or dual
   writer for earlier report projections.
4. Remove `mutationTesting { threshold.set(...) }`. Each public Acceptance
   Method must detect every mutation exactly attributed to its AC.
5. When using `--spec`, select every public Acceptance Method in a test class or
   move selected methods into a dedicated class before formal Verify.
6. Restore reviewer custody, then Check, Review, and Reseal before Verify. The
   Mechanical Seal and custody formats are current-version-only.

Both reviewer reports support invocation-only `--language zh-TW`. Property
completion counts require one matching current-run lifecycle, and discarded
generated inputs remain reviewer evidence. These capabilities were introduced
in the intermediate tags and are included in this direct-upgrade path.

## Requirements

Java 25 and a compatible Gradle version remain required. Formal Verify
continues to manage PIT 1.25.5 internally, and reviewer report bundles remain
offline and CSP-safe. The public Java/JUnit authoring API and machine evidence
schemas are unchanged by 0.0.24.

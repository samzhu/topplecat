# ToppleCat 0.0.26

ToppleCat 0.0.26 gives a Reviewer a clearer path from the complete selected
Spec to formal evidence for an agent's done claim, while keeping fast
feature-scoped verification distinct from the full-project verdict used in CI.
This release collects the work tagged since the last published GitHub Release,
0.0.10.

## Read the complete contract, then the evidence that matters

Before handoff, `toppleCatReview --spec ...` renders the complete selected
Markdown Spec with its Java Scenario, public and reviewer-owned Typed Case
Rows, Properties, and public Acceptance Method source. After formal Verify,
the reviewer-only Verification Report leads with the current outcome, then lets
the Reviewer open exactly the Acceptance Condition, expected-versus-actual
comparison, or technical evidence they need.

Both reports support invocation-only `--language en` and `--language zh-TW`.
ToppleCat-owned presentation is localized; authored contract text, producer
terms, evidence, Gates, and verdicts remain exact.

## Verify a finished feature without weakening the project seal

`toppleCatVerify` without a selection remains the complete-project command for
CI. A Reviewer can now obtain quick formal evidence for a finished feature with
either repeated Spec paths or repeated AC IDs, but not both:

```bash
./gradlew toppleCatVerify --spec specs/checkout/spec.md
./gradlew toppleCatVerify --ac AC-CHECKOUT-THRESHOLD --ac AC-CHECKOUT-VIP
```

The selected run limits public acceptance, Hidden Tests, Property-Based
Testing, and Mutation Testing to those ACs. Its `PASS` explicitly says that it
does not mean the complete executable contract passed. Contract Integrity,
`toppleCatSeal`, and `toppleCatReseal` always use the complete contract and
verification policy; Seal and Reseal reject `--spec` and `--ac`.

## Show five verification mechanisms without blurring their roles

The public project page now presents five clearly labelled synthetic checkout
demonstrations: Public Acceptance, Hidden Tests, Property-Based Testing,
Mutation Testing, and Contract Integrity. Each uses a fully synthetic report
excerpt and explains what the observed result supports and cannot prove.

Expected Consumption remains a required check that expected output was actually
asserted within Public Acceptance. It is no longer presented as a sixth,
parallel testing mechanism. The public page remains separate from actual
delivery evidence and implementation-agent handoff material.

## Upgrade from 0.0.10

1. Update the Gradle plugin and `topplecat-junit` dependency to `0.0.26`.
2. Stop publishing or parsing the retired `build/topplecat/reports/public/`
   bundle, and remove integrations with the retired `SpecView` projection.
   Reviewer tooling that consumes report JSON must use
   `topplecat.review-view.v7` and `topplecat.verification-view.v10`; there is
   no compatibility reader or dual writer.
3. Remove `mutationTesting { threshold.set(...) }`. Each public Acceptance
   Method must detect every mutation exactly attributed to its AC.
4. Use `toppleCatVerify` without `--spec` or `--ac` in CI. For a scoped local
   run, select either Spec paths or repeated AC IDs. Do not pass `--spec`,
   `--ac`, or `--language` to Seal or Reseal.
5. Restore reviewer custody, then run Check, Review, and Reseal before formal
   Verify. Mechanical Seal and custody formats are current-version-only.

## Requirements

Java 25 and a compatible Gradle version remain required. Formal Verify manages
PIT 1.25.5 internally; report bundles remain offline and CSP-safe. The public
Java/JUnit acceptance-authoring API is unchanged.

# ToppleCat 0.0.2

發佈日期：2026-07-25。

ToppleCat 0.0.2 修正四個會讓驗證結果不可靠的問題：預期結果只讀取卻沒有
比對、相同的 JSON 數值因小數位數不同而失敗、既有審閱資料沒有安全的更新
流程，以及關卡已失敗但命令仍回傳成功。

## 預期結果必須真的拿來比對

每個最外層的 `expected` 欄位，都是一項必須完成的驗證。只有
`ToppleCase.verify(...)` 能完成它。透過 `ToppleCase.expected(...)`
讀取時只會記錄為 `READ`，不會記成 `ASSERTED`；完全沒讀到則是
`UNTOUCHED`。啟用預期結果使用檢查後，這兩種情況都會讓該案例失敗。

換句話說，測試不能再靠「有把預期結果讀出來」過關，必須真的拿它和正式
程式的行為比較。

## 相同數值不再因格式不同而失敗

`ToppleCase.verify(...)` 現在會依照精確的數學值，逐層比較 JSON 數值。
因此 `200`、`200.0` 與 `200.00` 會視為相同，巢狀物件與陣列裡的數值也一樣。

這仍是精確比較，不是允許誤差的浮點比較。數值不同、物件或陣列結構不同，
以及數值和看似數字的文字，仍會判定失敗。

## 審閱合約可以安全更新

授權審閱者現在可以修改已隱藏的審閱案例組，不必丟掉原有的保管狀態。
請依序執行：

```text
toppleCatRestore
    -> 修改 src/hiddenTest
    -> toppleCatCheck
    -> toppleCatReview
    -> 審閱者確認審閱內容
    -> toppleCatUpdateEscrow
```

新版通過驗證前，原有的審閱資料會保持可用。更新失敗不會把舊資料一起丟掉。
本機稽核紀錄只保存數量，不寫入審閱內容；一般的 `toppleCatHide` 仍會拒絕
未經審閱的變更。

## 判定失敗時，Gradle 也會失敗

舊版可能出現證據已經是 `FAIL` 或 `INCOMPLETE`，Gradle 卻回傳成功的情況。
如果 CI 只看命令是否成功，就可能誤收一次失敗的驗證。

現在，只要整體判定是 `FAIL` 或 `INCOMPLETE`，`toppleCatReport` 和
`toppleCatVerify` 都會讓 Gradle 建置失敗。報告、證據、安全回饋與重新隱藏
審閱者原始碼仍會先完成。公開測試與審閱測試每次也會重新執行，不會把快取
裡的舊結果當成本次證據。

## 突變分數只計算公開測試

預設的 PIT 執行工作只使用 `sourceSets.test` 裡的公開測試類別與公開案例
資料列。審閱者案例與審閱者專用 JUnit 測試是另一組隱藏案例重測證據，
不會提高公開合約的突變分數。

若某個邊界條件必須由突變測試保護，就應把它放進公開的可執行合約。
ToppleCat 不會另外計算每個案例的突變分數，也不會猜測自訂執行方式的範圍。

## 相容性

`0.0.2` 的函式庫與 Gradle 外掛使用 `io.github.samzhu.topplecat` 座標。
本版使用 Java 25，並以專案隨附的 Gradle 9.1.0 Wrapper 驗證。ToppleCat
仍是 1.0 前的版本。

本版沒有變更公開的 `evidence.json` 或 `agent-feedback.json` 資料格式。

## 驗證

發佈內容已通過：

- 正確性、命令結束狀態、審閱資料保管與組態快取的針對性回歸測試；
- `./gradlew check`；以及
- `GRADLE_CMD=./gradlew scripts/verify-release.sh`，其中包含兩套獨立範例
  流程、突變測試關卡整合、文件與技能檢查，以及公開產物的隱私檢查。

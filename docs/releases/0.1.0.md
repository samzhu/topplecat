# ToppleCat 0.1.0

ToppleCat 0.1.0 connects the work on both sides of an agent handoff. Before
implementation starts, the Reviewer reads the selected Spec and the contract
that will actually run. After the agent says the work is done, the Reviewer
checks fresh evidence attributed to each AC. The delivery decision stays with
the human.

## Upgrade from 0.0.10

The last published GitHub Release was 0.0.10. Versions 0.0.11 through 0.0.28
were tagged but not published as GitHub Releases, so this upgrade includes the
reporting, verification, and workflow changes accumulated since 0.0.10.

1. Update the Gradle plugin and `topplecat-junit` dependency to `0.1.0`.
2. Stop publishing or reading `build/topplecat/reports/public/`. That report
   has been removed, and ToppleCat no longer produces public HTML for an actual
   delivery.
3. Remove integrations with the retired `SpecView` projection. Reviewer tools
   that read report `data.json` must use `topplecat.review-view.v7` and
   `topplecat.verification-view.v10`. There is no compatibility reader or
   dual-format output.
4. Remove `mutationTesting { threshold.set(...) }`. Each public Acceptance
   Method must now detect every mutation exactly attributed to its own
   Acceptance Condition.
5. Use `toppleCatVerify` without `--spec` or `--ac` for the complete CI run.
   Scoped Verify is for quicker Reviewer feedback on a recently completed
   feature; it does not replace full-project verification.
6. Do not pass `--spec`, `--ac`, or `--language` to `toppleCatSeal` or
   `toppleCatReseal`. Sealing always covers the complete contract and
   verification policy.
7. Reviewer custody and the Mechanical Seal are current-version-only. To
   upgrade an existing reviewer suite, Restore it, then Check, Review, and
   Reseal before formal Verify.

The public Java/JUnit Acceptance Method shape has not changed, so existing
acceptance tests do not need a source migration.

## Read the contract before handing work to the agent

`toppleCatReview --spec ...` produces a reviewer-only **Spec Review**. It shows
each complete selected Markdown Spec before the executable material bound to
its Acceptance Conditions: the Scenario, public and reviewer-owned Typed Case
Rows, Properties, and public Acceptance Method source.

This report is for reading before handoff. It does not run verification or
decide whether the upstream Spec is complete.

After the agent finishes the implementation, `toppleCatVerify` produces a
reviewer-only **Verification Report**. It starts with the current Aggregate
Verdict and the ACs that need attention. Public Acceptance, Hidden Tests,
Expected Result Check, Property-Based Testing, and Mutation Testing remain
separate under each AC.

Both reports work offline, include everything they need in the bundle, and use
a restrictive Content Security Policy. The Implementation Agent still receives
only the public Java/JUnit contract and safe `agent-feedback.json`, never
reviewer-owned rows, private diagnostics, or either HTML report.

## Check a finished feature without splitting the project seal

An unscoped `toppleCatVerify` still checks the complete contract and remains
the command to use in CI. For a quicker review of recently completed work,
select either repeated Spec paths or repeated AC IDs. Do not combine the two:

```bash
./gradlew toppleCatVerify --spec specs/checkout/spec.md
./gradlew toppleCatVerify --ac AC-CHECKOUT-THRESHOLD --ac AC-CHECKOUT-VIP
```

A scoped run limits Public Acceptance, Hidden Tests, Property-Based Testing,
and Mutation Testing to those ACs. The Verification Report lists the selection
and states next to a scoped `PASS` that the complete contract was not verified.

Contract Integrity, `toppleCatSeal`, and `toppleCatReseal` always use the
complete executable contract and policy. If a selected Acceptance Method shares a test
class with an unselected public Acceptance Method, select every AC in that
class or move the methods into separate classes before formal Verify.

## Mutation credit stays with the AC that earned it

Formal Mutation Testing uses ToppleCat’s managed
`topplecat-managed-v1` PIT 1.25.5 profile. Project PIT tasks, custom producers,
test targeting, and consumer reports remain outside ToppleCat evidence.

Mutation Attribution matches the complete Acceptance Method identity: class,
method, overload, and parameter types. Each AC must use its own public
Acceptance Method to detect every mutation covered by and exactly attributed
to that method. Detection by another AC does not count. Percentage thresholds
and project-wide mutation scores have been removed.

Mutation Testing also needs a passing Public Acceptance baseline. If the
original program already fails a public example, the Mutation result is
`INCOMPLETE`. In that situation, ToppleCat cannot determine how the unchanged
Acceptance Method responded to a separate temporary production change.

When an AC misses an attributed mutation, Verification Report shows the
assessed, detected, and undetected counts. Reviewer-only cards then explain
what changed, where the source was located when the evidence can establish it,
and that the AC’s unchanged public acceptance still passed. PIT outcomes and
selector relationships remain in technical evidence and never enter agent
feedback.

## See what happened before opening technical details

Each Acceptance Condition initially shows its ID, title, status,
plain-language result, and five safeguard outcomes. A safeguard that found a
problem or lacked enough evidence includes its reason in this first view.

Failed cases start with the authored input and a field-by-field comparison of
expected and actual values. Complete expected data, Scenario Steps, values
passed to Steps, raw failures, Gate verdicts, and producer details remain
available in separate disclosures.

A Reviewer can expand one AC, expand the full list in batches, or return the
report to key results. Links from the problem summary open the required content
before moving to it, so they do not land on a hidden target. Mutation Testing
terms have short localized explanations, while the original PIT terms remain
unchanged in technical evidence.

Property completion counts now require a complete lifecycle belonging to the
current run, with a matching sealed AC, complete Java method identity, and
source digest. Counterexamples and incomplete terminal outcomes remain visible.
Every input discarded by a generator is also retained as Reviewer evidence.

## Read reports in English or Traditional Chinese

Spec Review and Verification Report accept the invocation-only option
`--language en` or `--language zh-TW`. English is the default.

The option translates only ToppleCat-owned headings, controls, accessibility
text, explanations, and fallbacks. Selected Markdown, `@DisplayName`, `@As`,
Typed Case Rows, AC IDs, Gate names, verdicts, PIT outcomes, producer text, and
raw failures remain in their original form.

Changing the report language does not affect Delivery Scope, the Executable
Contract, Mechanical Seal, Current-run Evidence, Gate results, report JSON, or
`agent-feedback.json`.

## Keep public demonstrations separate from real deliveries

The public project page now has five synthetic checkout examples covering
Public Acceptance, Hidden Tests, Property-Based Testing, Mutation Testing, and
Contract Integrity.

Expected Consumption is an expected-output check within Public Acceptance, not
a sixth Independent Safeguard. The website examples explain the product to
human visitors. They are not evidence, agent feedback, or approval for an
actual delivery.

ToppleCat records `PASS` only when every required Gate passes in the current
run. This means the sealed contract passed the configured checks in that run.
It does not show that the Spec contains every business rule, and it does not
decide whether the Reviewer should accept the delivery.

## Requirements

Java 25 and a compatible Gradle version remain required. Formal Verify manages
PIT 1.25.5. Reviewer report bundles work offline and do not load external UI,
fonts, analytics, syntax highlighting, or a Mermaid runtime.

## Current technical documentation

The current user-facing workflow is published in English and Traditional
Chinese at the [official documentation site](https://topplecat.samzhu.dev/docs/).
It is a static, current-only projection with page-level Markdown and no Javadoc,
search, version selector, runtime translation, or actual-delivery report.

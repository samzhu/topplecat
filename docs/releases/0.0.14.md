# ToppleCat 0.0.14

ToppleCat 0.0.14 gives Java teams a clear review path for AI delivery: read the
complete executable contract before handoff, inspect a failure-first report
after formal verification, and leave the final acceptance decision to a human.

## Upgrade: stop consuming the retired public HTML

If you are upgrading from the previously published 0.0.10 release,
`build/topplecat/reports/public/` is no longer produced. Implementation agents
continue to receive the original public Java/JUnit contract and safe
`agent-feedback.json`; there is no replacement public HTML.

Code that directly consumed the retired `SpecView` projection must remove that
integration. Reviewer tooling that reads report `data.json` must use
`topplecat.review-view.v7` and `topplecat.verification-view.v9`. ToppleCat does
not provide a compatibility reader or dual writer for the earlier projections.

The public Java/JUnit authoring API, Gradle task names, `--spec` selection, six
Gate names, and machine evidence schemas are otherwise unchanged.

## Review the same contract before and after delivery

`toppleCatReview` writes the reviewer-only **Spec Review** before implementation
handoff. It presents each complete selected Markdown document, its diagrams,
compiler-described Scenario, public and reviewer Typed Case Rows, Properties,
and Acceptance Method source. It does not execute verification or decide
whether the upstream Spec is complete.

Formal Verify writes the reviewer-only **Verification Report**. The report leads
with ToppleCat's delivery recommendation and the concrete problems behind it,
then keeps Contract Integrity, Public Acceptance, Hidden Tests, Property-Based
Testing, and Mutation Testing separate. It does not blend them into a quality
score, and the reviewer still decides whether to accept the delivery.

Both reports are offline and self-contained. Unsupported or unsafe content is
escaped, and a local asset or diagram that cannot be rendered leaves a visible
fallback instead of silently disappearing.

## Trust the completed Property count

The Verification Report counts a selected Property as completed only when
**Current-run Evidence** contains exactly one `STARTED` event followed by one
matching terminal event for the run ID, Acceptance Condition, complete Java
method identity, and source digest. Duplicate, foreign-run, or incomplete
lifecycle evidence cannot increase the completion count.

Completion remains separate from outcome. A valid pass, counterexample, or
incomplete terminal event counts as completed evidence; the `PROPERTY` Gate
still reports the corresponding result.

## Work within a documented product boundary

The public Product definition now states when ToppleCat begins and ends. A
developer or reviewer uses it before a pull request to test an AI agent's done
claim and read the human reports. The team still owns Spec selection, CI or
workflow placement, delivery history, organizational approval, ordinary QA,
and project-specific PIT work.

Repository contributors also get an indexed design lifecycle and a
project-owned product-design skill. Accepted but unimplemented decisions stay
under `docs/design/`; completed designs are merged into current documentation
and removed instead of remaining as a second description of the product.

## Upgrade

1. Update the Gradle plugin and `topplecat-junit` dependency to `0.0.14`.
2. Stop publishing or parsing `reports/public`, and update reviewer report
   readers to the current projections if necessary.
3. Restore reviewer custody, then Check, Review, and Reseal before Verify. A
   Mechanical Seal is current-version-only.

## Requirements

Java 25 and the existing compatible Gradle and JUnit requirements are
unchanged. Formal Verify continues to manage PIT 1.25.5 internally, and report
bundles remain offline.
